# AGENTS.md

This file provides guidance to coding agents (Claude Code, and others that read `AGENTS.md`) when working with code in this repository.

## What this is

Eneverre is an Android client for the [eneverre-server](https://github.com/matiasdelellis/eneverre-server), a backend that consolidates IP camera streams from different manufacturers behind a single REST API. The app lists cameras, shows live RTSP streams (individually or as a live mosaic of all a location's cameras), supports PTZ control and a "privacy mode", plays back recordings, and can link Android TV devices via a user code. All UI code is Java (no Kotlin), targeting `minSdk 24` / `targetSdk 35`.

## Build & run

The toolchain is pinned by the build files and is **not** freely downgradable: AGP 9.3.1 / Gradle 9.7 / `compileSdk 37` (Android 17, SDK package `platforms;android-37.0`) and a JDK 21+ to run Gradle. `compileSdk` is dictated by the AARs: rtsp-client-android declares `minCompileSdk=37`, media3 1.11 declares 36. `targetSdk` is still 35 — a `targetSdk` bump is a runtime-behaviour change and a separate decision. `Dockerfile` and both GitHub workflows carry the same versions; move them together.

There is no test suite worth running (only the default empty `junit`/`espresso` stubs); don't expect `test`/`connectedAndroidTest` to validate anything.

```bash
./gradlew assembleDebug          # debug APK, no signing needed
./gradlew installDebug           # build + install to connected device/emulator
./gradlew assembleRelease        # release build — REQUIRES signing props (see below)
./gradlew lint                   # Android lint
```

`assembleRelease` triggers ABI splits (`armeabi-v7a`, `arm64-v8a` + universal) and **throws** unless all four signing properties are provided. Pass build-time properties via `-P` or `~/.gradle/gradle.properties`:

- `STORE_FILE`, `STORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD` — release signing (required only for release).
- `API_HOST` — optional. When set, it is baked into `BuildConfig.API_HOST`; the login screen then hides the host field and forces this host. When empty, the user types the host at login.

## Architecture

**Linear activity flow** (no nav component, no ViewModels despite the lifecycle deps being present — data is passed between activities as `Serializable` `Intent` extras):

```
SplashActivity → LoginActivity → CamerasActivity → ViewActivity
                                       │              ├─ Live tab     → LiveContainerFragment     (ViewPager2 → LiveViewFragment)
                                       │              └─ Playback tab → PlaybackContainerFragment (ViewPager2 → PlaybackFragment)
                                       └─ MosaicActivity (ViewPager2 → MosaicFragment: live grid per location)
```

- `SplashActivity` checks `SecureStore` for saved credentials, calls `cameras` to validate them (or `status` for a `monitor` account), then routes to `CamerasActivity` (success), `MonitorActivity` (monitor), or `LoginActivity` (no creds / a `401`). Before validating, the opt-in app lock (below) may send the launch through `LockActivity`; validation starts only after unlocking. A failure that is **not** an auth rejection — no server reachable, timeout, `5xx` — does not go to login: it stays on the splash, keeps the session, and shows an error panel with **Retry** and **Log out** (the latter clears the session and opens login, the only way to edit the host when the server moved).
- `LoginActivity` validates the host URL, calls `cameras` as a credential check, and on success persists the token pair **and the role** to `SecureStore`; a `monitor` account goes straight to `MonitorActivity` instead of the camera list.
- `CamerasActivity` groups the flat camera list into `Locations` and shows them in a `RecyclerView` (`LocationsAdapter` → nested `CamerasAdapter`). Each location header has a grid button (`OnLocationClickListener`) that opens `MosaicActivity` (handing it *all* the `Locations` plus the index of the tapped one); tapping an individual camera opens `ViewActivity`. Also hosts the "link device" flow (`device_verify`). Its toolbar has a single Settings action (gear) instead of the loose overflow entries.
- `SettingsActivity` is the configuration hub: **Security** (opt-in app lock, change password), **Account** (my sessions, user management for admins, sign out) and **Application** (check for updates, about), with the server and version in the footer. `util/Logout` is the one sign-out flow used from here, the camera list, the monitor screen and the splash. "Change password" opens `ChangePasswordActivity` in **voluntary** mode (asks for the current password and returns here); the `must_change_password` gate still opens it in mandatory mode (no Back, opens the camera list on success). The admin-only user entry is hidden for other roles (the endpoints are gated server-side too).
- `CameraSettingsActivity` edits one camera's live settings (admin only, `capabilities.settings`): day/night mode (4-way selector — the snapshot can't tell "manual" apart from a fixed mode, so only the selector remembers), illuminators (IR cut/850/940, white — shown only in Manual mode), audio in/out and motion detection. Every control PUTs its own change to `camera/{id}/settings` and re-reads the snapshot, so the screen repaints with camera-confirmed values. A PTZ section (shown when `capabilities.ptz`) offers the recalibrate command plus recording the camera's current position as its configured Home or Privacy position: the position is read from `ptz/position` (degrees) and saved by patching the admin `GET/PUT camera/{id}/config` fields (`home_x/home_y` / `privacy_x/privacy_y`), the same way the web frontend's camera dialog edits them (the PUT rebuilds the media pipeline, so the live stream reconnects). Reached from the sliders icon in `ViewActivity`'s live top bar (next to privacy, gated on `SecureStore.isAdmin()` and the capability; the endpoints are also admin-gated server-side).
- `MosaicActivity` is a `ViewPager2` host (`MosaicPagerAdapter`) that **swipes between locations**, one `MosaicFragment` per location, so you can go from one location's grid to the next without returning to the camera list. The toolbar title tracks the paged location, and a toolbar icon toggles the **view mode** (below) for every page. Fragments read the current view mode through the `MosaicHost` interface. The mode is persisted in `AppPreferences` and pushed to the page on screen (the only one registered as a `MosaicHost.LayoutModeListener`); pages offscreen at the time pick it up when they resume. Note the toolbar is hidden in landscape, so the toggle is only reachable in portrait — it carries over because it's persisted.
- `MosaicFragment` shows the live grid of *all* the cameras of one `Location` at once (`MosaicAdapter`). Every visible cell is its own `RtspPlayerView`, i.e. an independent RTSP session. Streams are tied to view attachment — a cell starts on `onViewAttachedToWindow` and is released on `onViewDetachedFromWindow` (prefetch disabled) — so only on-screen cells stream and the concurrent-RTSP count stays bounded by what fits. Cells never request audio; a tap opens the full single-camera `ViewActivity` — or retries the stream in place when that cell is showing the failure icon — and a pinch (or double tap) zooms that cell's picture in place — a `VideoTouchListener` per cell whose `TransformTarget` is the player, reset whenever the cell is rebound or stops. Unzoomed the listener leaves the drag to the grid, so scrolling still works; zoomed it claims it to pan. The adapter is attached in the fragment's `onResume`/detached in `onPause`: `FragmentStateAdapter` caps every non-current page to `STARTED`, so **only the location on screen streams** (an offscreen page holds no RTSP session, and nothing streams in the background) — the same `setMaxLifecycle` trick `ViewActivity` uses across tabs. The toolbar is hidden in landscape for a full-screen grid, along with the system bars (same `util/SystemBars` as `ViewActivity`). Because every cell shares one signed path token, the adapter also owns the wall's single refresh path (`CameraRefresher`): a cell that needs a fresh URL triggers at most one automatic `GET /api/cameras` per attached session, then **every** cell gets the new URL in place and only the stopped ones restart — never one request per cell, and never a rebind of the whole wall.
  Two **view modes**, switched from the host's toolbar icon. Cells have no intrinsic height: the fragment measures the viewport and hands `MosaicAdapter.setCellHeight` the height for the current mode, which is why the adapter is only attached once the grid has been laid out. That resize happens **in place** on the cells already on screen — going through `notifyDataSetChanged()` would recycle every holder and so tear down and reconnect every RTSP session on a mere mode switch or rotation. Only cells bound afterwards read the height from the adapter's field.
  - *Scrolling grid* (default): columns by orientation/count (portrait: 1 full-width column; landscape: 2 for ≤4 cameras, 3 beyond) and 16:9 cells, so the grid scrolls when the cameras don't fit and only the on-screen ones stream.
  - *Fit to screen*: rows × columns chosen so **every** camera of the location is on screen at once, each row taking an equal share of the viewport height — nothing scrolls, and by construction every camera of the location streams simultaneously. The page's background goes black (the scrolling grid keeps the theme's) so the gutters, the slack left by the integer division and any empty slot in the last row read as part of the wall. The split comes from `fitColumnsFor`, which picks the layout whose cells land closest to 16:9 for the viewport's own shape (so orientation needs no special case).
  Both modes re-lay out from the `RecyclerView`'s layout-change listener, **not** from `onConfigurationChanged`: on rotation the latter still sees the old dimensions, which would size the cells wrong and restart every stream twice.
- `ViewActivity` holds one `Location` and is the single host for its cameras, with a `BottomNavigationView` switching between a **Live** and a **Playback** tab. Each tab is a container fragment (`LiveContainerFragment` / `PlaybackContainerFragment`) wrapping a `ViewPager2` that swipes through the location's cameras. Both pagers stay synchronized on the same camera position, and tab visibility is driven with `FragmentTransaction.setMaxLifecycle` — the hidden tab is capped to `STARTED` so its visible page pauses, leaving at most one player streaming at a time. Also handles Picture-in-Picture and orientation. In landscape, where the toolbar and bottom tabs are hidden, it also hides the status/navigation bars (`util/SystemBars`; transient, so an edge swipe reveals them) and the video fills the display; portrait keeps the app chrome and the system bars. Both this layout and the mosaic set `android:keepScreenOn`, so watching is not interrupted by the display sleeping. Entering PiP passes the video's window bounds as `setSourceRectHint` (`LiveViewFragment.videoBounds()`): without it the system cross-fades the whole window, and whatever the app has not redrawn yet at the new size — the task's starting window, i.e. the app icon — shows through the transition.
- Fragments communicate with their host through interfaces, **not** by iterating `getSupportFragmentManager().getFragments()`: container fragments call `OnCameraChangeListener` on the activity as pages change; `LiveViewFragment` reports privacy toggles via `LiveViewFragment.OnPrivacyChangeListener`; the playback pager shares a current timestamp across pages via `PlaybackTimeHost`.
- `CameraPagerAdapter` / `PlaybackPagerAdapter` are `FragmentStateAdapter`s producing one `LiveViewFragment` / `PlaybackFragment` per camera.
- `LiveViewFragment` is the core live view: RTSP playback, PTZ controls, privacy toggle, mute, zoom/pan gestures, snapshot/share, and two-way audio / push-to-talk (see Two-way audio). `PlaybackFragment` mirrors it for recordings — but plays via Media3/ExoPlayer, not VLC (see Video) — adding a `TimelineView` scrubber and clip download.

### Networking (`api/`)

- `ApiClient` is a **singleton** built from `(url, accessToken, refreshToken)` (either token may be `null`). It owns the Retrofit instance and the base URL is `<host>/api/` (with port if present). `getInstance(url, access, refresh)` (re)initializes it and throws `IllegalArgumentException` on a malformed URL; the no-arg `getInstance()` / `getApiService()` throw `IllegalStateException` if it was never initialized.
- Auth is **Bearer access-token + refresh-token based** (Basic auth was dropped because the backend re-ran a PBKDF2 password hash on *every* request — ~hundreds of ms each, which made PTZ feel ~2s slow). **The username/password are never stored** — only the token pair (in `SecureStore`). A **registered OkHttp interceptor** attaches `Authorization: Bearer <accessToken>` to every request (except the token-minting `auth/login` / `auth/refresh` calls); call sites do **not** pass it explicitly.
  - `LoginActivity` exchanges username/password (+ a `device_name` label) at `auth/login` for a pair `{token (access, 24h TTL), refresh_token (90-day sliding TTL)}`, persists it, then fetches `cameras`. The password is used once and discarded.
  - A **registered OkHttp `Authenticator`** handles `401`s: it `POST`s `auth/refresh` with the stored refresh token, gets a **rotated** pair back, **persists it to `SecureStore`** (the refresh token changes on every refresh, so this is mandatory), updates the in-memory tokens, and retries. Concurrent 401s are serialized and collapse to one refresh. If refresh itself `401`s (refresh token expired/revoked) it gives up and the `401` propagates → `ApiCallback` reacts centrally through `util/SessionExpiry` (clear the session, keep the host, restart the task on login, once) instead of letting each screen show its own credentials toast; `CameraRefresher` does the same for the RTSP URL refresh. The `auth/login` / `auth/refresh` paths are excluded, since a `401` there is bad credentials, not a dead session.
  - `ApiClient`'s OkHttp client uses a **5 s connect timeout** (read/write keep the defaults): the backend is usually a LAN appliance, so "server down" should surface quickly in the splash panel and in command errors instead of waiting the 10 s default.
  - On app open, `SplashActivity` calls `ApiClient.refreshSessionIfExpiringSoon(...)` **before** validating: if the access token is missing or within `REFRESH_THRESHOLD_SECONDS` (1h) of its stored `expires_at`, it refreshes up front so requests don't trip a 401 mid-session. A failed proactive refresh is non-fatal (the reactive authenticator still covers it). This is why `SecureStore` also persists the access token's `expires_at`. Token writes (login, reactive + proactive refresh) all funnel through `ApiClient.setTokens(access, refresh, expiresAt)`, which updates memory **and** `SecureStore` together so they never drift.
  - "Cerrar sesión" (`CamerasActivity` menu) calls `auth/logout` (best-effort token revocation), clears the session via `SecureStore.clearCredentials()` (the host is kept, so login comes back pre-filled), and returns to login.

### Roles & camera ACL (`api/model/Role`, `util/SecureStore`)

The server has four fixed roles, and the app derives its UI from them instead of only `is_admin`:

| Role | Phone UI |
|---|---|
| `admin` | Everything, plus user administration and camera settings. |
| `user` | Live, playback, PTZ, privacy, talk and events. |
| `viewer` | Live and events only: **no Playback tab**, no PTZ/privacy/talk. |
| `monitor` | No cameras at all: lands on `MonitorActivity` (server status). |

- The role is persisted in `SecureStore` alongside `is_admin`; `Role` holds the constants and the `canViewCameras`/`canPlayback`/`canOperate`/`isMonitor` helpers. A session cached before roles existed falls back to `is_admin` (admin/user), and `SplashActivity` forces one `auth/refresh` to learn the real one (`SessionManager.refreshSessionIfExpiringSoon` refreshes when `!hasRole()`).
- `auth/refresh` returns `role`/`is_admin` best-effort, so a role changed server-side is picked up on renewal. A `403` from a capability-gated call means "the role may be stale": `ApiClient.refreshRole(...)` rotates the pair and re-reads the role, then the UI repaints (`LiveViewFragment` re-applies its controls, `CamerasActivity` routes a demoted monitor account, `SplashActivity` re-validates). A `403` is **never** treated as a dead session — only a `401` clears the credentials.
- UI gates: `ViewActivity.updatePlaybackTabEnabled` requires `canPlayback()`; `LiveViewFragment` requires `canOperate()` for the privacy action, the PTZ region, the privacy-exit button and the talk FAB; admin menus stay `isAdmin()`-only.
- **Camera ACL** is per-user and server-enforced: `GET /api/cameras` and `/api/status` are already filtered, and a camera outside the ACL answers `404` on single-camera endpoints. The client needs no ACL logic beyond refreshing: `CamerasActivity.showCameras` replaces the model with the authoritative list, and a `404` on a command asks `CameraRefresher` whether the camera is gone — `ViewActivity.onCameraUnavailable` then closes the view and `CamerasActivity` reloads via `RESULT_CAMERA_GONE`.
- Admin user management: `UserEditActivity` has a role dropdown (`Role.ALL`) and a "Cámaras permitidas" multi-choice dialog backed by `GET/PUT /api/users/{username}/cameras` (`UserCameras`). "All cameras" sends `{"restricted":false}`; "Save" sends `{"restricted":true,"camera_ids":[...]}` (an empty list means none). The ACL button is hidden for admins, who bypass the ACL.
  - In debug builds a `HttpLoggingInterceptor` at `BASIC` level is also added (status line only, never credentials). RTSP/live is **unaffected** — `Camera.getRtsp()` carries its own per-camera signed path token, separate from the user's password.
- `getPlaybackStreamUrl(...)` builds a recording-playback URL with **no** inline credentials; the player authenticates through the app's OkHttp client, whose `BearerInterceptor` stamps the current token on every request (a rotation mid-session is picked up, and a 401 is refreshed and retried by `TokenAuthenticator`). OkHttp strips the `Authorization` header when a redirect changes host, port or scheme, so a redirect cannot leak it. (There is no inline-credential `getPlaybackUrl` anymore — it went away with the VLC-based playback.)
- Retrofit callbacks should extend `util/ApiCallback<T>` instead of implementing `Callback<T>` directly: it splits success / HTTP-error / transport-failure, routes the latter two through `util/ApiError` for a localized message, and by default toasts it (override `onError` to extend). For `Void` endpoints, `onSuccess` receives `null`.
- API DTOs live in `api/model/` (`Camera`, `Recording`, `UserCode`, `VerifyStatus`, plus the auth pair `LoginRequest`/`LoginResponse` and `RefreshRequest`/`RefreshResponse`), Gson-annotated with `@Expose`/`@SerializedName`. View-layer models (`Location`, `Locations`, `Cameras`) live in `model/` and are derived from the API DTOs (`Locations` groups `Camera`s by `getLocation()`).
- `Camera` distinguishes **capability** (does the camera *support* a feature) from **state** (is it *currently* on): the nested `capabilities` object (`hasPlayback()`/`hasPtz()`/`hasPrivacy()`/`hasThumbnail()`/`hasTalk()`) is the source of truth for what UI to offer, while the flat `privacy` field is the mutable current privacy state (`getPrivacy()`/`setPrivacy()`, toggled at runtime and synced in `Cameras.update`). The UI gates controls on the capabilities: the privacy menu item, the PTZ controls, the talk button, and the Playback bottom-tab (`ViewActivity.updatePlaybackTabEnabled` per current camera; `PlaybackFragment` also shows a "no recordings" empty state for unsupported cameras).

### Video (`player/`)

Two players, split by use case — **live uses rtsp-client-android, recording playback uses Media3/ExoPlayer**:

- **Live (RTSP)**: `RtspPlayerView` is a `TextureView` driving the `RtspProcessor` of [rtsp-client-android](https://github.com/alexeyvasilyev/rtsp-client-android) (`com.github.alexeyvasilyev:rtsp-client-android`, JitPack) directly — **not** the library's own `RtspSurfaceView` widget. The view **is** the player — there is no separate player object to attach, own or release: it is declared in the layout (`R.id.live_video`, `R.id.cell_video`), `playUri()` starts and `stopPlayback()` ends the session. One class serves the single-camera view and every mosaic cell. It replaced libVLC once the library gained playback volume (`volume` as a 0..1 gain), which was the only thing it lacked for this app. RTSP over TCP, low-latency `MediaCodec`, H.264/H.265 + AAC/G.711. Note the library validates **no** TLS certificate on `rtsps://` (`NetUtils.FakeX509TrustManager` accepts anything), so an `rtsps` URL from the backend is encrypted but not authenticated — unlike under libVLC.
  **Why a `TextureView` and not the library's widget**: a `SurfaceView` is a separate compositor layer that the window only punches a hole for, so it ignores its parents' clipping. Magnifying one mosaic cell spilled the enlarged picture over the neighbouring cells — through *their* holes — while the single-camera view looked fine only because opaque window content happened to cover the overflow. There is no public API to clip a `SurfaceView` (`setClipBounds` only crops with the `@hide` `setEnableSurfaceClipping`). A `TextureView` draws inside the view hierarchy: it clips like any view, and `setTransform` magnifies the **content** while the bounds stay put, which is what `VideoTouchListener.TransformTarget` drives. The cost is a texture copy per frame that a `SurfaceView` avoids — paid on every cell of the grid.
  Driving `RtspProcessor` means depending on the library's inner API: its constructor takes a Kotlin function type that builds the decode thread for a given `Surface`, bridged by a method reference to the named `newDecodeThread` (no app source names `FunctionN`, but javac still needs `kotlin-stdlib` on the **compile** classpath to resolve the signature — the AAR only brings it in at runtime, as do okhttp/Material/AndroidX, so the APK is unchanged). That constructor is the piece most likely to break on a library upgrade.
  Four more things `RtspPlayerView` adds on top of the library, all of which will bite anyone who uses the raw widget:
  - **The URL is the credential.** `Camera.getRtsp()` returns a per-camera signed path token — `rtsp://<host>:<port>/<camera-id>/<exp>.<sig>` — valid six hours and scoped to that camera. There is no `user:pass@` userinfo and no RTSP `Authorization` header: `playUri()` hands the URL to the library untouched, and the last path segment must never be logged (`RtspUrl.redact`). An already-playing session survives token expiry; a **new** connection needs a fresh URL from `GET /api/cameras`. The server sends `rtsp` **empty** when it advertises no live feed (relay off, privacy on, or outside the recording schedule), so an empty URL is a state the UI must handle, not a crash.
  - **Refreshing before connecting.** `CameraRefresher` (in `api/`) owns the freshness policy and the request: a start refreshes first when the URL is missing, its token expires within 30 minutes (`RtspUrl.REFRESH_MARGIN_MS`), or the camera list is older than five hours. `markFresh()` is called wherever a list arrives (`CamerasActivity.showCameras` also), and concurrent refreshes collapse into one `GET /api/cameras` — which is what lets the mosaic recover a whole wall with a single request. `LiveViewFragment` caps the proactive attempt at one per stream (reset on a clean connect) so a wrong device clock cannot loop; its one-shot error-driven refresh stays as the last line of defence.
  - **Aspect ratio.** The decoder stretches the picture to whatever bounds it gets, so `applyContentTransform()` fits it to the stream's ratio (from `onRtspFrameSizeChanged`) in the **content matrix**, together with the zoom — the view itself always fills what the layout gave it, and `setOpaque(false)` lets the black parent show through as letterbox bars, as VLC did. It is deliberately not an `onMeasure` override: a measurement of ours survives a layout that skips it, and a rotation then left an odd-ratio camera sitting in its pre-rotation box while the 16:9 ones (whose box matches the cell anyway) looked fine. `onSizeChanged` re-fits, so the picture cannot be stale with respect to the bounds it is drawn in.
  - **Surface readiness.** Playback needs a live surface, but callers stream from `onResume` / view attachment, before the texture exists. A URL set too early is remembered and started from `onSurfaceTextureAvailable`, and restarted if the texture is destroyed and recreated (rotation, Picture-in-Picture). The decoders are stopped *before* the texture goes away — they are writing into it.
  - **One error per session.** The library reports a dead stream as a failure *and* a disconnect, and reports our own `stop()` as a disconnect too. `Listener.onError` fires once per session and never for a stop the app asked for. That goodbye lands on the main thread **after** the session stops counting as started, so stops are counted (`pendingGoodbyes`) and a new stream waits for the outstanding one: otherwise a cell torn down and restarted — which is what rebuilding the grid does — inherits the dead session's goodbye and comes up already showing the failure icon. `onRtspFirstFrameRendered` / `onRtspFrameSizeChanged` also arrive on the **decoder** thread, not the main one — the view posts them.
  `LiveViewFragment` requests audio and drives `setVolumePercent` (0–100) from the volume slider / global mute; mosaic cells call `setAudioEnabled(false)`, so they never even request the audio track. Snapshots come from `TextureView.getBitmap()` (`snapshot()`), not the `PixelCopy` in `util/Snapshot` — that one is still what recording playback uses, since Media3 draws on a `SurfaceView`. Every cell is an independent session — there is no shared engine to own anymore, which is why `MosaicHost` no longer hands one out.
- **Recording playback**: Media3/ExoPlayer over the server's **HLS VOD** surface, in three layers:
  - `Media3Player` — thin ExoPlayer wrapper (**mechanism only**): the app's OkHttp client behind Media3's `OkHttpDataSource` (so `BearerInterceptor` stamps the token per request and `TokenAuthenticator` refreshes on a 401; OkHttp also drops the header when a redirect changes host, port or scheme), playlist ops, position polling, and surfacing each load error's HTTP status. No retry/skip policy.
  - `HlsPlaybackController` — the **policy**. Requests `recordings/hls/playlist.m3u8?start=&end=` for a six-hour window around the seek, so ExoPlayer plays one continuous CMAF playlist instead of a chunk per 10 s of footage. The server collapses coverage gaps and emits `EXT-X-PROGRAM-DATE-TIME`, so the playlist's presentation time is **not** wall-clock: the controller keeps the window's segment list and maps the player position back to an absolute moment (and the initial seek into the playlist) by walking it. Reaching the end of a window opens the next one; only the end of the footage reports `onPlaybackEnded`. `recordings/get` is still what clip export uses. It also watches the last rendered video frame (`Media3Player`'s `VideoFrameMetadataListener`): when playback advances for more than 3 s without a video frame — a camera that stalled its video but kept sending audio — the UI shows an "audio only" overlay over the player instead of a black picture, and hides it as soon as frames resume.
  - `PlaybackFragment` — **UI only**: drives the controller and reacts to its `Listener` (buffering spinner, absolute time → `TimelineView`/`PlaybackTimeHost`, retryable error → Snackbar with "Retry").
- **Error handling**: a `404` on the playlist means the window has no footage (treated as the end); `5xx`/transport failures stop and offer Retry, which re-requests the window from the last reported moment. Segment-level retries are ExoPlayer's (`DefaultLoadErrorHandlingPolicy(1)`).

### Two-way audio / push-to-talk (`talk/`)

Only for cameras with `capabilities.talk` (the backend flags this when the camera INI defines a `backchannel` URL). `TalkClient` streams the mic to `ws(s)://<host>/api/camera/<id>/talk` (URL from `ApiClient.getTalkUrl(...)`), authenticating with the same Bearer header on the WebSocket upgrade (OkHttp can set it; browsers can't). See `doc/TALK.md` in the **eneverre-server** repo for the wire protocol.

- **Flow**: open socket → send the codec handshake (`{"sampleRate":16000}`, plus `"codec":"aac"` or `"codec":"opus"` on the encoded paths) → server replies `{"status":"ready"}` (`onReady`) → send binary audio: mono **S16LE PCM** (server resamples to 8 kHz + G.711 — always works), raw **AAC-LC** access units (16 kHz wideband), or raw **20 ms Opus** packets (RFC 7587 passthrough). The codec is picked from `capabilities.talk_codecs` — Opus preferred (when the device has a MediaCodec Opus encoder, see `TalkClient.hasOpusEncoder()`), then AAC, else G.711 (`Camera.supportsTalkAac()`/`supportsTalkOpus()`). The socket is **send-only** (half-duplex — the camera's own audio is heard through the normal live stream).
- **Session vs transmission are decoupled**: `start()` opens the socket; `setTransmitting(true/false)` gates mic capture. This is why the UI (below) connects first and only holds the mic while push-to-talk is pressed. On the AAC/Opus paths a single long-lived session thread runs the `MediaCodec` encoder from `ready` and streams **encoded silence** while the button is up (the server forwards those codecs verbatim, so nothing else warms the camera's decoder — unlike G.711, where the server streams its own silence); the mic itself is only opened while transmitting.
- **Capture thread owns the `AudioRecord`**: on release, the fragment only flips `transmitting=false`; the thread finishes the in-flight `read()`, **sends that last chunk**, then stops/releases the recorder itself (no cross-thread release, no clipped tail). `setMicGain` scales samples in place. The socket closes only on `stop()` (panel closed), where OkHttp flushes queued frames before the close frame.
- **UI** (`LiveViewFragment`): a mic FAB toggles "talk mode", which swaps the PTZ control region for a panel (title + close, mic-gain slider, camera-volume slider → drives `VlcPlayer.setVolume`, and a circular push-to-talk FAB disabled until `ready`). Needs the runtime `RECORD_AUDIO` permission (requested on first press). Errors surface by toast: `409` = another client already talking, others = generic failure.

### Persistence & misc utils (`util/`)

- `SecureStore` — singleton over `EncryptedSharedPreferences`; stores the host, the token pair, the access expiry, the account's role and the admin flag. `clearCredentials()` (logout, dead session) removes the tokens and everything derived from the account but **keeps the host**: it is configuration, not a credential, and login pre-fills it.
- `Logout` — the single sign-out flow (confirm, best-effort server-side token revocation, clear the session and restart the task on login), used from the camera list, the monitor screen, the splash and Settings.
- `AppPreferences` — singleton over plain `SharedPreferences`; non-sensitive prefs (global mute, mosaic view mode, opt-in app lock).
- `Snapshot` uses `PixelCopy` to grab a bitmap from the active `SurfaceView` (the `RtspPlayerView` itself for live, the Media3 `PlayerView`'s surface for playback); `Download` writes snapshots/clips to `Downloads/Eneverre` and shares via the `FileProvider` (`${applicationId}.fileprovider`, paths in `res/xml/file_paths.xml`).

### App lock (`util/AppLock`, `LockActivity`, `EneverreApp`)

Opt-in (off by default) and toggled from Settings → Security ("Bloqueo con huella o PIN"). It gates the **UI**, never the session: the stored tokens are untouched, so a failed or cancelled authentication cannot log the user out. It uses the device's own biometric/PIN through `androidx.biometric` (`BIOMETRIC_WEAK | DEVICE_CREDENTIAL` when the platform supports the combination, biometrics alone otherwise).

- `EneverreApp` registers `AppLock` as an `Application.ActivityLifecycleCallbacks`. A cold start initializes `locked` from the preference; a return from the background after **30 s** (`startedActivities` going 0→1) sets it and launches `LockActivity` over the resumed screen.
- `SplashActivity` checks the lock in `onResume` (after the lifecycle callback has decided) and starts `LockActivity` for a result, so a shared-event link cannot skip the gate; validation of the stored session only starts once unlocked. `LockActivity` cannot be dismissed with Back (it moves the task to the background) and finishing it without authenticating never reveals the app.
- A fresh login calls `AppLock.unlock()` (the login itself proves identity). The lock is skipped when there is no session or the device has no screen lock, so it can never trap the user behind a screen it cannot verify.
- No `FLAG_SECURE`: the system still shows the app's last frame in the recents thumbnail. That (and the rtsps certificate gap) is a separate hardening step.

## Conventions

- **Java only**, AndroidX, view binding is enabled (`buildFeatures.viewBinding true`) but most activities still use `findViewById`.
- Material 3 with Dynamic Color themes; `usesCleartextTraffic="true"` is intentional (self-hosted HTTP backends).
- Async calls use Retrofit `enqueue` (not coroutines/RxJava), with callbacks extending `util/ApiCallback<T>` so errors are mapped to localized messages via `util/ApiError` and surfaced (default: toast). Some screens still additionally route back to login on auth failure.
- Dependencies all go through the version catalog (`gradle/libs.versions.toml`); `app/build.gradle` only references `libs.*`. The JitPack repository is declared in `settings.gradle` (rtsp-client-android is published there).
